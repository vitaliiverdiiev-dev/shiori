# Shiori — M03.2.2: Repeated Practice, Balanced Shuffle & On-Demand Hints

## Context

M03.2 and M03.2.1 have been completed and pushed to `main`.

The Kana trainer now supports automatic advancement after correct answers, correction of incorrect answers, keyboard navigation, session restoration and first-attempt statistics.

We want to improve the experience for users who practice the same characters many times in one sitting.

This task contains four targeted improvements:

1. Configurable total number of questions per round.
2. Balanced randomization across repeated characters.
3. An always-available, on-demand answer hint.
4. The ability to Skip after an incorrect answer.

Do not create a new training engine or refactor unrelated functionality.

## 1. Configurable question count

On the existing Kana selection page, allow the user to configure the total number of questions in a practice round.

Example:

- Selected Kana: 10.
- Requested questions: 100.
- Result: each selected Kana appears 10 times.

Default the question count to the number of selected Kana, preserving the existing one-appearance-per-round behavior.

For counts that are not divisible by the selected set size, distribute appearances as evenly as possible.

Example:

- Selected Kana: 10.
- Requested questions: 23.
- Every Kana appears at least twice.
- Three randomly chosen Kana appear once more.

Requirements:

- Use an accessible numeric input.
- Validate positive safe integers.
- Support at least 100 questions.
- Use a reasonable, clearly communicated upper bound only if justified.
- Show the resulting total question count before starting.
- Keep the configuration simple and visually consistent with the selection page.
- Preserve the setting when navigating between selection and practice.
- Do not confuse total questions with the number of unique selected Kana.

An active round must retain its original question count and order. Changing the configuration must not silently modify an existing round.

Starting a new round must use the currently configured selection and question count.

## 2. Balanced randomization

Inspect the existing Fisher–Yates implementation.

Do not simply duplicate each Kana ID several times and shuffle the entire resulting array without considering distribution.

Instead:

1. Start with the unique selected Kana IDs.
2. Build independently shuffled cycles containing each selected Kana once.
3. Concatenate complete cycles.
4. For a partial final cycle, select the required number of distinct Kana from another shuffled cycle.
5. Avoid identical adjacent Kana at cycle boundaries whenever the selection contains at least two distinct Kana.

One selected Kana is a valid special case: repeated adjacent appearances are unavoidable.

Properties:

- Total question count is exact.
- Every question refers to a valid selected Kana ID.
- Occurrence counts differ by at most one.
- Every complete cycle contains each selected Kana exactly once.
- Each cycle is independently shuffled.
- Refreshing or resuming does not reshuffle the queue.
- Starting another round produces a new random arrangement.

Use the existing Fisher–Yates helper where possible.

Do not introduce weighted randomization, adaptive learning, spaced repetition or a new randomness library.

### Important session-model implication

The old session model expected each question ID to be unique.

That assumption is no longer valid for repeated practice.

Review and update:

- Queue representation.
- Attempt-to-question association.
- Reducer transitions.
- Session storage validation.
- Retry behavior.
- Existing tests.

A Kana ID identifies a character, not a unique occurrence within a practice round.

Use a question index or equivalent minimal occurrence identity wherever required.

Do not deduplicate the generated question queue.

Preserve backward compatibility with existing saved rounds where reasonably possible.

Do not change stable catalog IDs.

## 3. Always-available answer hint

Remove the verbose incorrect-answer message that reveals:

- The correct reading automatically.
- The user's previously submitted answer.

Instead, provide a small hint control near the answer input.

Use a suitable existing Lucide icon, such as Lightbulb or HelpCircle.

The hint must be available before answering and after an incorrect answer.

### Hint behavior

- The answer is hidden by default.
- Clicking or tapping the icon reveals the canonical romaji reading.
- Keyboard users must be able to activate it.
- The control must have an accessible name.
- The answer must not depend on mouse hover.
- The hint resets when moving to another question.
- The revealed answer must not modify the input automatically.
- Opening a hint must not submit or advance.
- Preserve predictable input focus and mobile keyboard behavior.

Prefer a small official shadcn/Base UI disclosure or popover pattern.

Avoid large dialogs, intrusive overlays, unnecessary animations and new custom primitives.

### Incorrect-answer UI

After an incorrect submission:

- Keep the red border and red focus ring.
- Keep the field editable.
- Select the incorrect text when appropriate so the user can replace it quickly.
- Show only concise feedback such as "Try again".
- Do not automatically reveal the correct answer.
- Keep the hint available.
- Enter or Check revalidates the current input.

After a correct answer, preserve the existing green success state and automatic advancement after 400 ms.

## 4. Hint usage and statistics

Track whether the user revealed a hint for the current question.

Store this information with the attempt or question state.

Important distinctions:

- Correct on the first attempt without a hint.
- Correct on the first attempt after revealing a hint.
- Incorrect first attempt, later corrected.
- Skipped.

Do not treat using a hint as proof of independent recall.

Prefer a small `hintUsed` flag rather than introducing a large new outcome framework.

Preserve the existing first-attempt outcome and `corrected` semantics.

A later correct answer must not erase an earlier incorrect attempt.

If a hint was used before the first correct submission, preserve that fact for future M03.3 progress calculations.

Update the summary only as needed to distinguish assisted answers from independent correct answers. Avoid inflated claims about learned or mastered characters.

For "Retry missed", include characters answered incorrectly, skipped or completed using a hint. Deduplicate Kana IDs in the retry selection rather than accidentally creating several retry questions for the same missed character.

## 5. Restore Skip after incorrect answers

Currently, an incorrect answer forces the user to enter the correct reading before continuing.

This should not be mandatory.

Requirements:

- Skip remains available while answering.
- Skip remains available after an incorrect attempt.
- Skip immediately advances to the next question.
- If no attempt was recorded, record a skipped outcome.
- If an incorrect attempt was already recorded, preserve that incorrect outcome and advance without recording another attempt.
- Preserve the existing correction flow when the user chooses to keep trying.
- Prevent duplicate records.
- Do not allow Skip to interrupt the locked 400 ms correct-answer transition.

Users should be able to practice quickly without being forced to copy the revealed answer.

## 6. Session restoration and timer safety

Preserve existing sessionStorage and user identity isolation.

Update stored-data validation for repeated question IDs and hint metadata.

Check:

- Refresh during normal input.
- Refresh during incorrect feedback.
- Refresh while a hint is open.
- Refresh during the 400 ms correct-answer transition.
- Leaving and resuming.
- Starting a new round before an old timer fires.
- Repeated Kana IDs in the same queue.
- Corrupted or outdated saved data.
- Account switching.

Avoid recording an attempt twice when a round is restored.

Preserve the reducer's existing stale-timer protection.

Do not create a global state store or a separate scheduling system.
