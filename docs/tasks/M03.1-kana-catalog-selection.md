# Shiori — M03.1: Kana Catalog & Selection

## Project context

Shiori is a self-hosted Japanese writing-system and vocabulary practice application.

The frontend foundation (F01–F06) is complete.

We are beginning M03 — Kana Trainer.

IMPORTANT PRODUCT CLARIFICATION:

Shiori is NOT a Japanese textbook, guided curriculum, or gamified language-learning app.

Users freely select which Japanese characters they want to memorize and practice. The application presents characters, accepts typed answers using the device's native keyboard, checks answers, and tracks progress.

The long-term product includes:

- Hiragana training.
- Katakana training.
- Mixed Kana training.
- Kanji training.
- Japanese vocabulary training.
- Multiple practice directions.
- User-managed vocabulary.
- Persistent progress.

No XP, streaks, artificial rewards, mandatory lessons, or custom on-screen keyboards.

The supplied product direction has already been approved.

## 1. Inspect the existing architecture

Before changing code:

- Inspect the frontend domain structure.
- Inspect backend modules and existing Drizzle patterns.
- Inspect the current route registry.
- Inspect the existing navigation and responsive layouts.
- Inspect conventions for schemas, validators, data mapping and tests.

Decide where the Kana catalog belongs.

Kana content is fixed reference data, but the application will later store user-specific practice attempts and progress.

Do not automatically create database tables for every piece of static reference data.

Compare:

- A versioned, typed static catalog.
- A database-backed seeded catalog.

Choose the simplest approach that supports stable Kana identifiers, future persisted progress and predictable content updates.

Document the decision briefly.

## 2. Kana catalog

Provide complete modern foundational Hiragana and Katakana data for practice, including:

- Basic kana (gojūon).
- Voiced and semi-voiced kana (dakuten/handakuten).
- Common contracted combinations (yōon).

Model each practiceable written form with:

- A stable unique identifier.
- Script: Hiragana or Katakana.
- Written form.
- Canonical romaji.
- Accepted alternative romanizations where linguistically appropriate.
- Group/category.
- Stable display ordering.
- Correspondence to its equivalent form in the other script, where applicable.

Keep shared phonetic relationships explicit without confusing distinct written characters.

Examples:

- あ → a
- ア → a
- し → shi
- ち → chi
- きゅ → kyu
- ギョ → gyo

Handle cases in which different kana share a common romanization, such as じ/ぢ and ず/づ.

Do not collapse distinct characters merely because their pronunciation or romanization is similar.

Use a documented, consistent romanization convention, preferably modern Hepburn for the primary displayed reading.

Do not invent uncommon combinations to fill a theoretical grid.

Do not include obsolete or historical forms by default unless there is a clear product reason.

Pay particular attention to the completeness and correctness of the data. Include focused catalog integrity tests.

## 3. Kana selection UI

Create real authenticated selection screens for Hiragana and Katakana.

Users should be able to:

- Browse all available characters.
- Understand their groups.
- Select individual characters.
- Deselect individual characters.
- Select an entire row or group.
- Select all available characters.
- Clear the current selection.
- See how many items are selected.

Suggested sections:

- Basic Kana.
- Dakuten / Handakuten.
- Yōon combinations.

Preserve the natural Japanese ordering rather than alphabetically sorting by romaji.

Include convenient bulk-selection controls or presets only where useful.

Avoid building a complex generic selection framework.

### Selection semantics

- Individual selection must be independent and predictable.
- Group selection should handle partially selected groups.
- Selection state must not be confused with learning progress.
- Never display fabricated mastery or progress percentages.
- Do not persist fake progress data.
- Ensure selections are based on stable Kana IDs.

For M03.1, local selection state is sufficient unless a small justified persistence mechanism is already available.

Do not design saved custom sets yet.

## 4. Responsive UI

The application must work comfortably on desktop, tablet and mobile.

On desktop:

- Use an appropriately sized, readable Kana grid.
- Avoid excessive whitespace between related controls.
- Make it easy to select multiple characters quickly.

On mobile:

- Adapt the grid to the available viewport.
- Preserve readable characters and accessible touch targets.
- Avoid horizontal overflow.
- Keep primary selection actions understandable.

Use the established Shiori Stone/Indigo theme and typography rules.

Do not copy the green visual style of reference applications.

Use the official shadcn components where practical.

Avoid excessive cards, borders, decorative elements or visual noise.

Japanese characters must remain visually prominent.
