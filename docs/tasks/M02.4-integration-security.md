# M02.4 — Authentication integration, adversarial tests and release-quality verification

Status: **Not authorized until M02.3 review**. Read `../specs/M02-authentication-design.md` and all previous phase handoffs.

## Goal

Evaluate and harden the integrated M02 authentication implementation as a whole. Fix defects found by real security and user-flow tests; remove unjustified abstractions/comments and ensure production-minded behavior *without claiming production deployment readiness*. No new features or major rearchitecture except a necessary fix.

## 1. Full lifecycle tests

Use clean isolated PostgreSQL and a normal browser/client as available:

- Fresh migrate → CLI bootstrap exactly one admin → sign-in → protected home/health/settings → logout → old cookie denied.
- Invite mode CLI create/list/revoke, one-use invite registration → **no session on signup** → normal sign-in → protected access.
- Closed mode rejects signup directly; `open` cannot accidentally be enabled without verified email delivery; public registration-capability endpoint reveals only safe mode information.
- Expired/revoked/wrong-email/replayed/concurrently claimed invitations; partial failures and retries do not create two accounts.
- Role boundary: guest protected denial (401), ordinary user privileged denial (403), no unintended admin plugin endpoints (including impersonation, password reset on other accounts, role modification) even as admin if not approved.
- Password invalid/current/new/confirm cases; Unicode/length; generic invalid login; rate limits (valid and wrong-user traffic); no secret leakage.
- Session expiry, revocation from another device, change-password other-session revocation, network outage during `useSession`, login redirect sanitization and cache isolation between two users.
- Swagger/OpenAPI vs real runtime responses, SDK generated types and query options, deterministic generated diff, health/readiness remains publicly callable and accurate; web renders `/status` via TanStack Query.
- Fresh install/second startup preserves data and does not regenerate migrations or overwrite `.env`.

## 2. Security review and threat model

Review with KataKit `backend-architecture`, `testing`, `code-quality`, `ui-design`, `quality-gate` as relevant. Include:

- secret management (`BETTER_AUTH_SECRET`, cookies, no argv/logging), env guards, HTTPS/proxy trust and CORS/Origin/CSRF;
- brute-force/rate-limit and storage assumptions, generic auth error surfaces, duplicate-email enumeration and synthetic user response;
- session fixation/caching/revocation, account switching/private query cache, safe redirect normalization;
- authorization on **backend**, not routing only; future owner setup must never be a publicly unguarded endpoint;
- invite code hashing/entropy, expiry, atomicity and `used`/`revoked` semantics with race tests;
- dependency audit, audit of any unexpected public routes, permission grants and external requests;
- no obvious plaintext user data in `/health`/`ready`, logs, stories or generated SDK.

Do not add security theater (unused scanners, giant custom auth abstractions, fake '100% secure' statements). Record confirmed issues, risks, and intentional deferrals separately. If critical security check fails, phase FAIL/BLOCKED; do not bypass to produce a green report.

## 3. UI/UX and operational verification

- Mobile-first sign-in/signup/settings, visible loading/empty/error states, input autofocus only where accessible, keyboard navigation, screenreader names/errors, password manager and paste, coarse-pointer touch targets, semantic CSS tokens.
- Check in browser at narrow and wide viewports; if browser automation unavailable label NOT RUN and provide manual steps; don't imply visual QA.
- Ensure no unused UI/route/files/folders. Check consistent architecture and generated-code exclusions. Review diff for accidental churn, secrets and performance regressions.
- Update README, `docs/02-tech-stack.md`, `docs/03-architecture.md`, `docs/05-roadmap.md` and `.env.example` only to reflect **actual verified M02 implementation**. No fake future installer instructions or premature milestone-complete label.

## 4. Run the quality gate

Discover exact scripts before invoking. Expected from current repo:

```bash

```

Also: clean DB migration rerun, API integration smoke, API SDK codegen drift check, `pnpm dev` browser smoke, dependency audit/security checks appropriate to changed dependencies, and clean `git diff`/secret review. Do not simply assert `pnpm audit` exists or that a failure was unrelated without investigation.

Record each as **PASS / FAIL / NOT RUN / BLOCKED**, with command, environment and real result; make fixes for caused failures, do not edit unrelated files for style. Security-critical checks cannot be silently skipped. If required Docker/browser unavailable, report limitation and provide exact local reproduction steps, not a false PASS.

## 5. Exit criteria and deliverable

- All M02 decisions implemented and verified, or clear explicitly accepted deferrals from the design; no unreviewed critical/high findings.
- Exact endpoint/route/CLI map documented, production environment requirements and secure default behavior explained, SQL migrations committed in working tree and reproducible, generated SDK consistent.
- Final report in categories: confirmed implementation, test evidence, deviations, residual risks, future backlog and recommendation for M03.
- **Do not commit/push/PR/deploy** without explicit user authorization. Stop with final audit and wait for independent review.
