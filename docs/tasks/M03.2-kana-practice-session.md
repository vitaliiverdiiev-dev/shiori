# Shiori — M03.2: Kana Practice Session

## Context

M03.1 — Kana Catalog & Selection — is completed, reviewed, committed and pushed to `main`.

We now have:

- A typed static Hiragana/Katakana catalog with stable IDs.
- 104 practiceable entries per script.
- Canonical romaji and alternative readings.
- Selection screens at `/kana/hiragana` and `/kana/katakana`.
- Individual, row, section and bulk selection.
- Existing authenticated layouts, typed routing, theme, React Compiler, shadcn/Base UI and tests.

We are implementing **M03.2 — Kana Practice Session**.

Shiori is a self-directed Japanese writing-system memorization trainer, NOT a textbook, curriculum or gamified learning application.

Users freely choose characters and practice them by typing answers.

**Goal:** Connect the existing Kana selection pages to a fully functional client-side typing practice session.

Do not implement backend progress persistence. That is M03.3.

## Phase 2 — Connect selection to practice

Users must be able to:

1. Select any number of Kana, from one to all available entries.
2. Start a practice session with the selected characters.
3. Return to selection without unexpectedly losing that selection.
4. Resume an unfinished session.
5. Explicitly start a new round with the current selection.

Add a real Start Practice action to both existing selection pages.

It must be disabled when nothing is selected.

Use the existing route registry to add protected, lazy-loaded practice routes.

Prefer straightforward routes such as:

- `/kana/hiragana/practice`
- `/kana/katakana/practice`

Inspect the existing routing conventions before deciding.

Do not introduce a new routing framework.

If a practice route is opened without a valid session, redirect to its corresponding selection page or display an appropriate recovery action.

Do not display an empty or broken practice screen.

## Phase 3 — Practice session model

Implement a focused Kana-specific session model.

A session should retain:

- Script.
- Selected Kana IDs.
- Shuffled question order.
- Current question position.
- Completed answers and outcomes.
- Current unsubmitted input, where appropriate.
- Completion state.

Use stable Kana IDs from M03.1.

Ensure that the session refers to valid catalog entries.

### Question order

- Include every selected character once per round.
- Shuffle the selected IDs once when creating a new round.
- Do not reshuffle on component re-render.
- Do not reshuffle when resuming a session.
- Handle a single selected character correctly.
- Support the full catalog without an arbitrary question limit.

A standard unbiased shuffle algorithm is sufficient.

Do not introduce weighted randomness, spaced repetition or a scoring engine.

### State transitions

Model the following behavior clearly:

- Waiting for answer.
- Showing feedback.
- Advancing to the next question.
- Completing the round.

Use the simplest appropriate React state mechanism.

A small reducer is acceptable if it makes transitions easier to understand and test.

Do not create a generic TrainingEngine, plugin system or state-machine framework.

## Phase 4 — Answer validation

For M03.2, implement only:

**Kana → Romaji**

The user sees a Hiragana or Katakana character and types its reading using Latin letters.

Examples:

- あ → a
- きゅ → kyu
- シ → shi
- チ → chi

Place the answer-checking logic in the Kana domain.

Do not hardcode validation rules inside React components.

### Normalization

Support reasonable text normalization:

- Ignore surrounding whitespace.
- Compare ASCII letters case-insensitively.
- Match the canonical romaji or an explicitly accepted alternative.
- Do not use approximate string similarity.
- Do not silently accept arbitrary misspellings.

Do not let normalization collapse distinct Kana identities.

### Romanization decisions

Update the existing catalog and tests to implement the approved decisions:

1. Display `wo` for を and ヲ in the selection catalog.
2. Accept both `wo` and `o` as answers for these characters.
3. Preserve the existing stable IDs.
4. Keep `o` as the reading of お and オ.
5. Keep modern Hepburn as the general display convention.
6. Accept common, documented IME-style alternatives where appropriate, including spellings such as `jya` and `cya`.

Keep accepted spellings explicit and deterministic.

Do not implement a general-purpose Japanese IME or transliteration library.

Test ambiguous and exceptional cases, including:

- じ / ぢ.
- ず / づ.
- お / を.
- ん.
- しゃ / じゃ / ちゃ and their variants.

Do not broaden the catalog to extended Katakana or obsolete Kana in this task.

## Phase 5 — Practice interface

Implement a clean, focused interface.

### Required elements

- Leave/Back action.
- Current question number and total.
- Large, clearly rendered Kana.
- One text input for romaji.
- Submit action.
- Skip action.
- Feedback after submission.
- Next action.
- Completion summary.

Use Shiori's existing Stone/Indigo design tokens.

The practice experience should be visually simple and distraction-free.

A dedicated focus layout without the ordinary application sidebar is acceptable if it fits the existing routing and layout architecture.

Do not alter the application's general Sidebar merely to implement this screen.

Use official shadcn components where appropriate.

Do not copy the green reference UI literally.

### Desktop input

- Use the physical keyboard.
- Enter submits an answer.
- After feedback, Enter advances.
- Keep focus behavior predictable.
- Avoid forcing the user to click the input for every question.

### Mobile input

- Use the operating system's native keyboard.
- Do NOT build a custom on-screen keyboard.
- Do not force the mobile keyboard open immediately on page navigation.
- Keep the input and primary action visible when the native keyboard opens.
- Avoid unnecessary keyboard dismissal between questions.
- Keep controls accessible at narrow widths.
- Support the mobile keyboard's Enter/Done action where feasible.

Ensure IME composition events do not accidentally submit incomplete text.

Use appropriate text-input attributes, such as disabling unwanted capitalization, spellcheck and autocomplete where relevant.

Avoid fighting browser-native input behavior.

## Phase 6 — Submission and feedback

### Correct answer

- Record the attempt as correct within the session.
- Show concise positive feedback.
- Allow the user to advance.

### Incorrect answer

- Record the attempt as incorrect.
- Show the canonical correct reading.
- Keep the user's submitted answer understandable.
- Allow the user to advance.

### Skip

- Record a distinct skipped outcome.
- Do not classify it as an incorrect submitted answer.
- Advance to the next question.

### Additional rules

- Do not automatically skip feedback immediately after submitting.
- Prevent duplicate submissions.
- Prevent repeated Enter presses from recording multiple attempts for one question.
- Do not treat an empty answer as a submitted answer.
- Do not silently advance after invalid or empty input.
- Ensure feedback is accessible to keyboard and screen-reader users.

Keep the interaction fast and predictable.

No animated celebrations, XP, streaks, rewards or artificial penalties.

## Phase 7 — Completion summary

At the end of a round, display:

- Total questions.
- Correct answers.
- Incorrect answers.
- Skipped questions.

Offer:

1. Practice the same selection again.
2. Retry only incorrect and skipped characters, when there are any.
3. Return to selection.

If every answer is correct, do not show a meaningless Retry Mistakes action.

A retry round should contain the corresponding Kana IDs without duplicates and use a new shuffled order.

Do not call session results "mastery", "learned percentage" or long-term progress.

M03.3 will introduce persistent statistics and progress semantics.

## Phase 8 — Session continuity

M03.2 remains client-side only.

Use a minimal mechanism such as `sessionStorage` for preserving:

- Current selection.
- In-progress practice session.
- Question order.
- Completed attempts.
- Current position.
- Unsubmitted answer when appropriate.

Requirements:

- Refreshing the page should not silently restart the round.
- Returning to selection should preserve the selected set.
- Resuming should not create duplicate attempts.
- Starting a new round must be an explicit action.
- Completed session data should not be mistaken for persistent learning progress.
- Corrupted or outdated stored data should fail safely.
- Validate restored Kana IDs against the current catalog.
- Avoid stale session data being presented after an account change.

Inspect the existing authentication architecture and use its existing identity or session boundaries.

Avoid adding new authentication requests or inventing a second auth state manager.

Document that browser session storage is temporary and does not provide cross-device persistence.

Do not use IndexedDB, PostgreSQL, a global state framework or a new dependency without a demonstrated need.

## Phase 9 — Ownership boundaries

Keep Kana-specific responsibilities inside `domain/kana`.

Expected responsibilities include:

- Catalog data.
- Answer normalization and validation.
- Selection logic.
- Session transitions.
- Kana practice UI.

Pages should remain thin route-level composition.

Use `shared` only for genuinely domain-independent components or utilities already justified by the application.

Do not move Kana concepts into shared merely because Kanji and Vocabulary might eventually use similar mechanisms.

Do not create a generic practice engine yet.

Future practice directions may use different validation rules, but M03.2 should implement only the approved Kana → Romaji direction.

Avoid unnecessary configuration and speculative extension points.
