## Fix 1 — enforce model/ boundaries for every import spelling (P1)

**Confirmed review observation:** the model-scoped `no-restricted-imports` regex in `eslint.config.js` rejects `../helpers/...` but does not itself match `@/domain/health/helpers/...`. The generic same-slice boundaries rule may permit that alias-based bypass.

Architecture invariant:

- `pages/<slice>/model/` and `domain/<slice>/model/` define contracts, constants, schemas and declarative configuration. They **must not import** the slice's `api/`, `helpers/`, `hooks/`, `store/` or `ui/`, nor React/React DOM or React-only hooks.
- Valid dependencies on `model/`'s own files and permitted domain-agnostic `shared/` contracts remain allowed.
- The same restriction applies regardless of **relative vs `@/` imports**, and to import/re-export forms as supported by the installed rule. Do not allow an import spelling change to defeat the boundary.
- Do not break normal imports **from** `model/` **into** helpers/hooks/ui. The prohibition is directional.

Implementation:

1. Review the actual ESLint Flat Config and `eslint-plugin-boundaries` setup; choose the **smallest reliable** mechanism (path-aware boundaries rules, correctly scoped `no-restricted-imports`, or a minimal tested local rule only if needed). Avoid a broad regex that bans all `@/domain/` imports from unrelated valid files.
2. Preserve the existing maximum relative traversal rule and external public-API restrictions. Avoid duplicating the same rule in several unrelated config overrides.
3. Extend `scripts/eslint-architecture.test.mjs` with **negative** fixtures representing `model/` imports of `helpers`, `api`, `hooks`, `store`, `ui` through `@/` as well as relative paths. Test both `pages` and `domain` paths as applicable.
4. Add **positive** fixtures: `model/` importing its own `./types` / `./schema` (when appropriate); valid `@/shared/...`; a hook/helper importing its own slice's model; valid external consumers importing a slice through its `index.ts`.
5. Include at least one `export ... from ...` invalid sample and verify whether static re-exports are covered. If dynamic `import()` is outside coverage, document that fact rather than saying all imports are protected.
6. Do not change the legitimate app dependency graph merely to make lint pass.

**Done when:** the previous absolute alias bypass is rejected in an executable test, valid imports still pass, and `pnpm lint` passes on real source.

## Fix 2 — remove presentation classes from model/ (P2)

**Confirmed review observation:** `domain/health/model/consts.ts` exports `dotColors`, which contains Tailwind classes; `ui/status-row.tsx` imports it. This makes a WHAT/contract layer own visual styling.

- Move `dotColors` (or rename it appropriately) into the owning `ui/` scope. Prefer the smallest coherent change: within `ui/status-row.tsx` if its component conventions/lint allow, or `ui/consts.ts` if separating the mapping is clearer. **No new global theme or styling infrastructure.**
- Keep semantic health status values and backend contracts in `model/`. Keep the value-to-CSS representation and Tailwind classes in `ui/`.
- Preserve the full status mapping (`checking`, `offline`, `online`, `unavailable`, `unknown`), `satisfies Record<StatusState, string>` or equivalent exhaustive type safety, light/dark tokens, accessibility and exact existing UI behavior.
- Delete `model/consts.ts` only if it becomes empty, and clean up imports without leaving dead files.
- Update architecture lint fixture(s) that currently use `dotColors` from `model/consts.ts` as a positive example; use a semantically valid model import instead.
- Add or adjust a focused test only where it protects meaningful behavior; no snapshot churn just for code movement.
