# M01.1 — Infrastructure, Diagnostics & One-Command Development

**Status:** COMPLETE (2026-11-11). M02 (authentication) not started.

## Context and objective

M00 (React/Vite, NestJS, design system) and M01 (PostgreSQL, Drizzle, migrations) are complete. The current root `pnpm dev` runs only `turbo run dev`, so it starts **web and API, not PostgreSQL**. A fresh checkout currently needs separate `.env`, `pnpm db:up`, `pnpm db:migrate`, and `pnpm dev` steps.

Make local development ready to use with **one command after dependency installation**:

```sh
pnpm install
pnpm dev
```

This should prepare a safe local environment if necessary, start/wait for PostgreSQL, apply **existing version-controlled** development migrations, then run NestJS (watch) and Vite (HMR). Also add basic database diagnostics and a convenient local database browser.

**Design principle:** Prefer a few straightforward scripts and small coherent modules. Avoid general orchestration frameworks, new dependencies without necessity, or speculative infrastructure.

## Required implementation

### 1. Dev startup command

- Change root `pnpm dev` so it starts **all required local development services** in order:
  1. Preflight Docker / Docker Compose availability and readable local configuration.
  2. If root `.env` is missing, create it **once** from the committed `.env.example` containing intentionally fake **local-development-only** values; never overwrite an existing `.env` or print credentials. Explain what happened. Avoid requiring manual setup after a fresh clone.
  3. Start PostgreSQL using existing `pnpm db:up` / `docker compose up -d --wait postgres`; fail clearly if it cannot become healthy.
  4. Apply **existing reviewed SQL migrations** with `pnpm db:migrate` against the local development database; fail fast on error. **Never auto-generate migrations or use `push`.** Guard this automatic step against accidentally targeting a non-local database; keep production migrations an explicit, separate operation. M01 has no actual domain migrations yet; the empty migration journal is expected.
  5. Start the existing Turborepo `dev` tasks (Vite + NestJS watch mode), preserving combined logs and Ctrl+C behavior.
- Keep `pnpm db:up`, `pnpm db:down`, and `pnpm db:migrate` individually usable. Consider `pnpm dev:apps` for running only Vite + Nest when the DB is already prepared. `pnpm dev` should be the obvious default.
- Idempotent: rerunning must not reset data, duplicate DB instances, overwrite `.env`, or regenerate migrations.
- Ctrl+C must stop **web and API development processes**, but need not stop PostgreSQL; its named volume must survive. Document `pnpm db:down`.
- Prefer a simple `pnpm` script chain with one tiny preflight/helper if required. Do not add an orchestration library or invent a background supervisor. Avoid complex cross-platform shell assumptions: macOS is our initial development target, but a portable Node solution is preferable.
- A missing Docker daemon / Docker executable or an inconsistent `.env` must produce an actionable error **before** launching the app servers.

### 2. Infrastructure folder organization

- Move existing PostgreSQL init assets from `docker/postgres/init/` to `infra/docker/postgres/init/` (or equivalently simple location). Update the root `compose.yaml` mount path and related docs/tests.
- Keep `compose.yaml` at repository root for straightforward `docker compose` commands. `compose.yaml` is the modern supported name; **do not** rename it to `docker-compose.yml`.
- Compose for local dev still runs **PostgreSQL only**. Vite/Nest remain local processes for HMR, debugging and fast feedback.
- Do **not** create production compose, API/Web Dockerfiles, AWS/Kubernetes config, reverse proxy, Redis or additional services in this milestone.

### 3. Optional DB browser for development

- Add `pnpm db:studio` for `drizzle-kit studio`, reusing the existing Drizzle database configuration. Keep its local server bound to `127.0.0.1` (do not expose on LAN/publicly).
- Do **not** start Studio as part of `pnpm dev`: it is an optional developer tool. No pgAdmin/Adminer Docker service is required yet.
- Document how to start it and that there are no business tables until the first real auth migration.

### 4. Database readiness endpoint

- Preserve `GET /api/health` as **liveness** independent from DB connectivity.
- Add `GET /api/ready` as **readiness** using the existing managed Drizzle/PostgreSQL connection to run a bounded `SELECT 1` or equivalent actual DB operation.
- On success: HTTP 200, stable small JSON indicating `status: 'ok'` and `checks.database: 'up'`.
- On database failure or query timeout: HTTP 503, stable small JSON indicating `status: 'error'` and `checks.database: 'down'`.
- Put a finite timeout on the DB check using supported pg/driver facilities, and handle connection errors without leaking credentials, hostnames, SQL, stack traces or other internal details in the HTTP response.
- Do not create a generic monitoring framework, a dependency registry, or a NestJS Terminus integration just for this simple check. Keep infrastructure independent from Japanese domain modules.

### 5. Frontend health diagnostics

- Extend the existing Shiori health/status UI to display both **API** and **Database** states, with checking/success/failure and a user-triggered retry. Reuse current design-system components and tokens; mobile-first.
- Frontend calls API only: never connect directly to PostgreSQL.
- If API liveness is unreachable, show **API offline** and **Database unknown** (not automatically offline). If API is online but readiness returns 503, show **API online** and **Database unavailable**. Both online when readiness succeeds.
- Keep requests bounded; avoid unhandled promise rejections, duplicated global clients, or introducing TanStack Query solely for this diagnostic screen.

### 6. Tests and verification

- Backend tests: liveness stays 200 with DB unavailable; readiness returns 200 for successful DB check and 503 for failure/timeout, with safe response shape. Mocking the database dependency for HTTP failure cases is acceptable; use the existing M01 `test:db` for real connection verification. Do not stop or destroy a developer's running Postgres container in automated tests.
- Frontend tests: all-online, DB-down while API-online, API-down => DB-unknown, and recovery after clicking **Check again**.
- Dev startup verification: with Docker available, `pnpm dev` from a fresh local setup starts Postgres, web and API; `GET /api/health` and `GET /api/ready` return expected responses. Rerunning with an existing DB and `.env` preserves data. Ctrl+C stops Vite and Nest but does not remove the DB volume. Verify missing-Docker or bad-config error handling without deleting data.
- Run/report `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`, `pnpm build-storybook`, `pnpm format:check`, and `pnpm test:db` when Docker is available. State environmental blockers rather than claiming unrun checks succeeded.

### 7. Docs and completion

- Update README development instructions to make `pnpm install` then `pnpm dev` the default path; clearly explain `db:studio`, `db:up`, `db:down`, `db:migrate`, and any `dev:apps` command.
- When verified, update `CLAUDE.md` and `docs/05-roadmap.md` to mark **M01.1 complete, M02 next**. Do not implement M02 until explicitly requested.
- Keep `pnpm review:zip` working; the export must exclude `.env` and all generated build/cache/database data while retaining safe `.env.example` and source/docs.
- No automatic commit, push, deployment or KataKit edits.

## Definition of done

1. After `pnpm install`, a developer can start the required dev environment with **`pnpm dev` alone**, given a working Docker installation.
2. Web + API run with live reload; PostgreSQL is healthy, persistent, and uses the existing loopback-only host binding.
3. Existing migrations are applied locally before app startup; failures prevent a misleading successful startup.
4. `/api/health` represents API liveness; `/api/ready` represents actual DB readiness; UI correctly distinguishes online/offline/unknown states.
5. `pnpm db:studio` provides optional local DB inspection, not a public service.
6. Relevant tests and checks pass or precise blockers are disclosed; no unrelated functionality or infrastructure added.
