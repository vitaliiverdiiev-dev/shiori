# M02.1 — Auth foundation, database and typed API pipeline

Status: **Implemented and accepted**. Prerequisite: M01.2 completed. M02 design: `../specs/M02-authentication-design.md`.

## Goal

Integrate a minimal **real, testable** Better Auth email/password backend with NestJS + existing Drizzle/PostgreSQL, protect routes appropriately, and establish OpenAPI → Hey API → Axios typed client pipeline with current diagnostics as the first real contract. This phase does **not** enable user registration flows, CLI administration, or frontend login forms. It validates critical integration assumptions before M02.2.

## Work packages (implement only necessary files)

### A. Compatibility feasibility checkpoint (first)

- Inspect actual Node/Nest/Drizzle/PostgreSQL/TS versions, existing env/database providers, `main.ts`, `app.config.ts`, `app.module.ts`, diagnostics and existing tests. Check **stable** published Better Auth, `@thallesp/nestjs-better-auth`, `@better-auth/drizzle-adapter`, Nest Swagger/OpenAPI + Zod bridge, Hey API and TanStack Query compatibility. Prefer installed supported versions; lock exact versions via pnpm lockfile.
- Confirm Better Auth route mounting under Nest global `/api`: exactly `/api/auth/*`; prevent `/api/api/auth/*`.
- Confirm body parser behavior for auth and non-auth endpoints; Nest global guard default; `@AllowAnonymous` for `/api/health` and `/api/ready`; `401` for a **real small private auth-check endpoint** (useful beyond smoke tests, not decorative).
- Determine real use of shared PostgreSQL pool and how to instantiate Drizzle & Better Auth without a second pool or framework circular dependencies.
- Investigate how to safely pass a one-time invitation code through the **actual** Better Auth sign-up HTTP body/hook path, and ensure other signup/account-creation endpoints cannot bypass policy. Investigate **documented and tested** transaction semantics for sign-up + future invite consumption; record whether supported adapter can join caller-managed transactions or identify a concrete limitation for M02.2. Do not claim solved if not proven.
- Investigate Admin Plugin capability: test role storage, first-admin path, and safest configuration to avoid exposing impersonation/set-password/set-role endpoints unnecessarily. Prefer no plugin if safe minimal restriction cannot be demonstrated; record choice for M02.2.

### B. Backend auth foundation

- Add `modules/auth/` consistent with backend standard; configure Better Auth securely with validated env (`BETTER_AUTH_SECRET`, base URL/origins/registration mode as needed) and email/password server auth. Preserve existing typed env parsing, health/readiness, application setup and shutdown behavior.
- Password length 15–128, no complexity classes; support Unicode/passphrases and don't trim passwords; use library's password hasher; `autoSignIn: false`. Block public sign-up initially (`closed` baseline) **at the real server auth endpoint**. `open` without email verification must fail config validation rather than enable public signup.
- Database-backed seven-day rolling sessions, no cookie cache; correct safe cookie settings under localhost vs HTTPS; keep trustedOrigins/CSRF checks. Provide a private endpoint / handler proving session-based protection where helpful (only one minimal example).
- Add Better Auth schemas for user/account/session/verification (and role fields if needed); ensure relations appropriate to pinned adapter. Merge into existing Drizzle configuration without unnecessary schema layers. Create and inspect **first committed SQL migration** via existing Drizzle Kit; don't run `auth migrate` with Drizzle. Verify migration on clean DB and idempotent repeated invocation. Preserve isolated DB test practice.
- Add actual server integration tests for login/sessions/protected access/public health, schema initialization and production-incompatible env handling. Fixtures/test credentials must be fake, isolated and non-secret.

### C. End-to-end API typing foundation (first real contract)

- Integrate Nest-generated OpenAPI with exact and stable operation IDs, schemas and status codes for `GET /api/health`, `GET /api/ready` (and optionally the tiny private endpoint); verify output reflects real HTTP responses and does not accidentally include secrets/admin routes.
- Prefer Zod runtime schemas as source where compatible with Nest OpenAPI; verify on actual emitted spec rather than trusting decorators. Reuse existing `zod` where available. Avoid duplicating DTO interfaces manually across FE/BE.
- Install/configure `@hey-api/openapi-ts` with Axios transport and TanStack Query plugin only as needed for real diagnostics SDK consumer in M02.3; generation deterministic and offline/reproducible from local spec, not requiring a live hosted server. Use `packages/api-client` only once the generated SDK is a real workspace dependency. Generated files are not hand edited; choose consistent commit vs regenerate policy and enforce drift check.
- Keep Better Auth endpoints out of generated SDK (Better Auth own typed client is authority). Confirm error/response types and API base route. Do not create a custom Axios request wrapper or duplicate generated query hooks.

## Required tests / evidence

- Real HTTP API responses: `/api/health` and `/api/ready` remain anonymous and correct on DB up/down; protected endpoint is 401 without session and 200 with real session.
- Correct cookie behavior for sign-in/sign-out under local same-origin; no auto-session from signup; after logout the old cookie is denied; invalid credentials fail generically.
- First migration applies to empty PostgreSQL DB and reapplying is safe; DB test workflow stays isolated.
- OpenAPI includes diagnostics with accurate response examples/schemas/status; generation works twice without untracked diff; generated client imports and compiles for supported TS project.
- Verify whether dangerous Admin endpoints are exposed, and record **actual denial tests** if using Admin Plugin. If cannot restrict, don't ship its default broad admin API.
- `pnpm lint`, `pnpm typecheck`, relevant `pnpm test`, `pnpm test:db`, `pnpm build`, `pnpm format:check`; other commands per `quality-gate`. Report precise statuses rather than claim unexecuted checks pass.

## Exit criteria / explicit handoff

M02.1 is complete only after foundation works with real DB/tests, type generation is reproducible, current diagnostics do not regress, and documented blockers for invitation atomicity are addressed or explicitly marked as blocking M02.2 pending user review. Report minimal package additions, changed paths, migration SQL, tested endpoint map and concrete invitation integration feasibility. **STOP**; no CLI invitation, no auth pages, no commits/pushes.
