# M02.3 — Frontend authentication, routes and server-state migration

Status: **Not authorized until M02.2 review**. Depends on real working Better Auth + invitation policy from M02.2. Read `../specs/M02-authentication-design.md`.

## Goal

Deliver a functional, mobile-first React SPA with guest/protected navigation, email/password forms, own-account and security pages, session lifecycle, and migrate current API/DB diagnostics to the agreed **generated Axios SDK + TanStack Query** path. Do not create public landing, admin UI or future setup wizard.

## 1. Architectural ownership and tools

- React Router 7 **Declarative Mode** for client-only routing; no React Router loaders/actions duplicating TanStack Query or a framework-mode migration.
- Better Auth React client created in **`domain/auth/config/auth-client.ts`**. Use native typed Better Auth hooks/methods for session, sign-in, sign-up, sign-out and password change. Never wrap `useSession` in TanStack Query or store its data in Zustand.
- TanStack Query 5 for other server data; integrate generated Hey API query/mutation options and Axios. No hand-maintained parallel `requests.ts` for generated endpoints; compose hooks only when they add real UX/business logic.
- RHF + Zod for forms. `model/` for schemas/types/constants, `helpers/` for transformations/mappers/validators, `hooks/` for React orchestration when needed, `api/` for meaningful domain request/query composition, `ui/` for local UI, `config/` for client configuration. No empty folders or deep barrels.
- Respect `app/pages/domain/shared` layer/public API rules, one top-level component per main `.tsx`, named exports, strict TS no `any`; CSS under `app/styles/`, component Tailwind via classes and semantic tokens.

## 2. Routes and layouts

- `/` protected existing home, never guest landing.
- `/sign-in` guest-only; on success internal safe redirect or `/`.
- `/sign-up` guest-only; query minimal public backend registration-capability endpoint (generated typed SDK) to determine current mode; when mode invite, form requires code; in closed/open-disabled, registration is not offered, and direct backend call remains rejected.
- `/settings/account` protected name change and **read-only email**.
- `/settings/security` protected current/new/confirm password, change-password revokes other sessions; sign-out and revoke other sessions.
- `/status` protected visual health/ready diagnostics, while backend `/api/health` and `/api/ready` remain public.
- Public/friendly `*` not-found state. `/admin/*` and `/setup` remain future only.
- Small app/auth layouts with `Outlet` only when they reduce repetition; don't scaffold unused nav. Use app's existing `product.config.json` for branding.

## 3. Session state and redirects

- Handle checking, authenticated, unauthenticated, and API-unavailable distinctly. No flash of protected content before initial check; do not globally wipe application for background refresh.
- Network failure != logout; show retry/state-specific feedback without leaking protected user content. Expired/revoked session redirects to `/sign-in`.
- After sign-in safely restore _internal_ destination only. Reject absolute, protocol-relative, encoded external and malformed redirects; default `/`. Avoid loops when a signed-in user hits guest routes.
- Sign-out, session removal and account switch purge user-private TanStack Query cache (and abort relevant in-flight requests) before subsequent signed-in user sees any data. Don't wipe unrelated public state unnecessarily.

## 4. Forms and messaging

- Sign-in: email, password, submit pending state, generic invalid-credential error; support browser autofill and password managers.
- Sign-up: name, email, password, confirm, invite code; 15–128 password policy, no arbitrary complexity class; paste/unicode/passphrases; show/hide. **Do not auto-authenticate**: show neutral completion/next-step text and link/redirect to sign-in **without claiming an account definitely exists**, because Better Auth may return synthetic success for duplicate email. Avoid revealing whether email already exists.
- Security: current/new/confirm password; require current password; `revokeOtherSessions: true`; show successful completion and meaningful error handling.
- Account: edit own name, show email (no change until verification flow exists).
- Messages map known Better Auth typed error codes, not raw unknown server responses. No nonworking Forgot Password link; no admin invite creation UI. Maintain labels, focus handling, aria error descriptions, keyboard submission and touch target sizing.

## 5. Health-check migration (required, not optional)

- Remove the old parallel hand-rolled `fetch/useEffect/useState/inFlight` diagnostic lifecycle and use TanStack Query on generated typed health/ready SDK as the consistent app data access standard.
- Preserve separately visible API/DB statuses and original READY semantics; DB down should not claim API down; timeout/error retry and manual refresh. Add tests for API down, DB down, recovery and user retry. Don't invent new caching abstractions.
- Ensure protected `/status` can still show diagnostic state if API unavailable and does not incorrectly show 'logged out' for network failures.

## 6. Test plan and verification

Write behavior-first tests with Vitest/RTL/MSW or current repo tools: protected/guest access, session loading/error/failover, redirect sanitization, sign-in/form errors, signup no-auto-login, invite-only screen, password/name forms, cache isolation A→B, health status recovery. Use realistic integration browser smoke via available tooling or explicitly report NOT RUN; don't claim screenshots inspected unless really inspected.

Run relevant `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`, `pnpm build-storybook`, `pnpm format:check`, `pnpm test:db` where needed, plus quality-gate. Avoid pointless snapshots or test inflation.
