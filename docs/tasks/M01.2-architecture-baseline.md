Create **only** directories justified by moved code, aiming for this organization:

```text
apps/web/src/
├── app/
│   ├── app.tsx                # Only App component, optional type Props and imports
│   └── styles/
│       └── index.css         # Existing global Tailwind/theme CSS, not rewritten

├── domain/
│   └── health/

│       ├── health-status.test.tsx
│       ├── api/              # Only actual requests; queries only if TanStack is ALREADY used
│       ├── model/            # WHAT: types/consts/contracts/config as needed
│       ├── helpers/          # HOW: validation, mapping, calculations as needed
```

This tree shows **ownership**, not a requirement to manufacture empty `api`, `model`, `helpers`, `hooks`, `ui`, `tests`, or store folders. Do not add `features`, `widgets`, `entities` layers. Don't introduce TanStack Query, Zustand, routing libraries, Zod, or new runtime dependencies just to fill these segments. No `store/` unless a real store already exists; future Zustand behavior belongs to the portable standard.

Specific migration guidance:

- Move root `app.tsx` composition into `app/app.tsx`, moving page-only layout/content into `pages/home/home-page.tsx`. Keep real product identity sourced from root `product.config.json`, without copying strings into components or importing `app` from `pages`. **Avoid a 3+ level relative import to the root JSON:** if necessary, configure one explicit Vite/TS alias for that exact canonical JSON (e.g. `@/product-config`), import it from `app`, and pass page-facing values through typed `HomePage` props. Ensure ESLint treats this narrow config alias as an allowed internal import rather than a cross-layer escape hatch. No second copy of product config.
- Split existing root `health-status.tsx` according to actual responsibilities: main domain component, HTTP request code, typed response contracts, semantic constants, pure checks/transformations, React request/retry state hook, and smaller UI as justified. **The main component file may contain only imports, optional `type Props`, and one named `export const HealthStatus` declaration.** Same rule for `HomePage` and root `App` component. Do not introduce unnecessary one-function files or wrappers to satisfy a drawing.
- Keep API/DB liveness/readiness UI and all current UX. When extracting readiness response checks, validate both `status: 'ok'` **and** `checks.database: 'up'`; do not mark malformed success as DB online. Preserve API offline → DB unknown. Preserve bounded requests and dedup/retry behavior. Add a focused DB down → restored → manual retry test if still absent. **Don't create a new feature or polling system.**
- Move the existing shadcn **Base UI** Button into `shared/ui/primitives/button/` and colocate its Storybook file; preserve styles, variants, mobile touch behavior and stories. Export it through `shared/ui/index.ts`. Do not replace it with Radix or recreate the component from scratch.
- Move `cn` from the old `lib/utils.ts` to `shared/helpers/cn.ts`, update component import paths. Remove obsolete now-empty `components/` and `lib/` directories after references are fixed.
- Move `index.css` into `app/styles/` and update `main.tsx`, Storybook preview and `apps/web/components.json` tailwind.css alias. No CSS Modules or local UI stylesheet files. Do not change token values except to fix a regression.
- Set `components.json` to route shadcn `ui` to `@/shared/ui/primitives` and `utils` to `@/shared/helpers/cn`. Make other aliases consistent and test a dry run or inspection of shadcn output semantics; CLI **does not** automatically create one directory per component. Document the after-install relocation rule, without building a generator.
- Migrate frontend tests to Architecture v1 location rules: **main component tests adjacent**; folder-eponymous component tests adjacent; other tests in **immediate local `tests/`** (not `__tests__`). `src/test/` for shared setup only. Adjust tests/config imports; avoid changing test behavior except the small health cases above.
- Maintain `@/` alias resolution in Vite, TS, Vitest and Storybook. All cross-slice imports through their `index.ts`, never deep imports; internal same-slice imports directly.

### C. ESLint and automated architecture enforcement

Implement **the agreed stable first iteration**, detailed in `code-quality-v1.md`:

- FE layer direction, cross-slice public `index.ts` restriction (relative and absolute imports), internal-barrel avoidance, maximum two `../` traversals, and meaningful BE boundaries.
- Strict main page/domain component-file rule (imports + optional `type Props` + one named `export const Component` at module top-level); main App if applicable. Use targeted AST-based enforcement if robust; don't pretend docs alone enforce this. Exempt generated shadcn primitives, stories and tests.
- Import groups: React, third parties, `@/` aliases, relative local — alphabetical **within each** and **zero blank lines** between groups; properly handle type and side-effect imports.
- Alphabetical named imports/exports, re-exports and eligible `type`/`interface`/function declarations. No dangerous global `const`/hook sorting.
- `id` **exactly first**, then A–Z for suitable object literals, interface and type properties. JSX props A–Z, preserving spread semantics. Add specific safety exceptions where reorder would change runtime behavior.
- `@typescript-eslint/no-magic-numbers` practical policy; don't require every 0/1 to be extracted, and don't duplicate semantically unrelated constants.
- Keep `pnpm lint` as a nonmutating check and add `pnpm lint:fix` if practical; ensure auto-fix behavior is verified without breaking Prettier or React hooks.
- Add runnable, focused **positive + negative lint examples** and `--fix` output checks. Prove both architecture import restrictions and the main-component rule. Test wrong key/import order and correct `id`-first order. Do not merely include plugin names/configuration as evidence. Don't commit temporary intentionally-invalid source files.
- Install only compatible stable packages required for these rules (typically Perfectionist and Boundaries). Avoid a custom rule framework; one tiny tested local rule is justified only if robust main-component enforcement otherwise fails. If a precise requirement cannot safely be enforced, document it as _manual_ with an explanation, not as a false pass.
