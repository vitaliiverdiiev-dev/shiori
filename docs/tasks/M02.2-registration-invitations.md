# M02.2 — First admin, registration policy and one-use invitations

Status: **Implemented and accepted**. Read `../specs/M02-authentication-design.md` and handoff from M02.1.

## Goal

Deliver the secure, reusable backend operations for initial admin bootstrap and invitation-driven account creation. A CLI is the **only M02 administrative entry point**, but business operations are reusable by future protected admin UI and setup wizard. No SMTP, no admin dashboard, no public web setup, no open registration.

## 1. Registration policy

- Validate `REGISTRATION_MODE`: `closed` (default) and `invite` functional; `open` reserved but **rejected/disabled** without implemented, tested email verification transport. Choose one documented configuration source (env), no second settings DB table in M02.
- Enforce policy at actual Better Auth signup endpoint on server. Provide a minimal, public, typed read-only registration capability endpoint (`closed`/`invite`) so the UI can choose its registration entry; do not expose invitation validity or email existence. Do not rely on hiding `/sign-up`. Existing users can sign in regardless of mode. Mode changes must not disrupt sessions.
- Better Auth `autoSignIn: false` and email-enumeration protections enforced in reality. If Admin Plugin changes response fields, configure/test `customSyntheticUser` appropriately so registered/unregistered emails do not yield distinguishable response shapes.
- Newly invited signups are always `user`, not `admin`, independent of provided body fields.

## 2. Safe one-time initial admin CLI

- Provide a documented **interactive local** command (name chosen consistently with scripts) that accepts name/email and a hidden password input; do not require AI or a browser to execute it; never pass secrets via argv, print them to stdout, place in shell history, logs or process env by default.
- Use Better Auth's supported server-side creation/hash and required role schema. Do **not** persist a second password hash scheme.
- Enforce an invariant that only uninitialized installation can bootstrap first admin: include concurrent attempts and crash safety. A naive `count users -> create` without DB-level guarantee is inadequate. Repeated attempts fail safely; do not provide a `--force` bypass that silently creates administrators.
- Do not expose a network endpoint for bootstrap in M02. The reusable application operation may later be called by an installer-secret-authorized Setup Wizard, with a separate authorization boundary.

## 3. Invitations

- Secure, high-entropy, unpredictable codes generated using cryptographic randomness; only _hash_ stored in DB; display raw code once on successful CLI creation, never on list/log/review. Code expires after seven days; tied to normalized email; single-use, revocable.
- Provide local commands for create, list metadata (not codes) and revoke, with safe validation and helpful errors; use one small CLI entry point or narrow modules, not a CLI framework.
- Prove the invite code reaches the actual Better Auth signup server hook/validator and cannot be bypassed through alternative account-creation endpoints. Sign-up must verify selected mode, code, expiry, revocation and email binding on server. Return safe errors without revealing stored code/hashes or account existence.
- **Critical invariant**: at most one account can be created using a given invitation even during concurrent requests, retries or partial failures. Investigate actual Better Auth Drizzle transaction hooks/APIs; show real PostgreSQL tests of atomic claim and account creation or a rigorously justified recovery protocol. Avoid declaring `before/after` hook sequence atomic.
- If true transactional integration cannot be achieved with available API, stop with documented blocker and safer specific alternatives. Never implement a merely optimistic `find invitation -> signUp -> usedAt` as final solution.
- Clarify normalization and uniqueness semantics for email with tests; do not make case-folding assumptions without DB constraints.

## 4. Admin privilege boundaries

- Confirm standard `admin/user` roles in persisted schema. Do not expose Better Auth Admin Plugin's dangerous default endpoints (impersonation, role changes, admin password reset, arbitrary account deletion) to admins or users unless necessary and explicitly restricted.
- Prove with real HTTP tests: unauthorized guest returns 401, user receives 403, disallowed admin operation denied even when the caller is admin. If plugin cannot enforce reduced permissions, remove it and implement minimal roles/CLI using supported backend APIs.
- Prevent losing last admin or creating unintended second bootstrap admin. Do not give admins implicit access to private learning data.

## 5. Security and tests

Test real PostgreSQL invariants and auth flow, not just mocked services:

- fresh and already initialized DB; race of two bootstrap commands; secrets absent from command line/logs; clean failure on DB outage;
- closed mode direct signup rejected; open mode configuration rejected; invite mode valid signup accepted but **no session cookie** issued;
- expired/revoked/wrong email/altered/reused code denied;
- two requests use same invitation simultaneously -> one account maximum;
- DB failure between account creation/invite consumption; rollback or documented proven recovery; retry outcome;
- duplicate-email privacy and synthetic success; an already existing email must not consume a valid invite or create a second account; permissions, CSRF/Origin, rate-limiting policy for auth endpoints;
- developer commands and clean migration still work.

Follow KataKit TDD and quality-gate. If any critical race/privilege escalation is unproved, M02.2 is **BLOCKED**, not PASS.
