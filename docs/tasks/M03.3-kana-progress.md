# Shiori — M03.3: Persistent Kana Progress

## Goal

Store every finalized Kana → romaji question in PostgreSQL, show per-kana statistics on the selection page across sessions and devices, and remove the visible success sentence from the practice screen.

Shiori is a self-directed memorization trainer: no XP, streaks, achievements, mastery percentages or mandatory lessons.

## Scope

In scope:

1. Practice screen: no visible success text after a correct answer (green border and ring, a check mark in the field, a screen-reader-only “Correct: …”, the unchanged 400 ms advance).
2. One persisted record per finalized question occurrence (round id + question index), keeping the M03.2.2 first-attempt semantics (`correct`, `correct` with hint, `incorrect` even if corrected later, `skipped` only before any answer; `corrected` and `hintUsed` as additional facts).
3. A shared, framework-free Kana catalog package that both the web app and the API use to validate kana ids and readings.
4. An authenticated, idempotent, batched API for recording attempts and a per-script progress summary.
5. A durable, user-scoped pending queue in the browser that never blocks practice and retries safely.
6. A minimal progress indicator on each Kana tile, a details table and a save status in the round summary.

Out of scope: spaced repetition, mastery scores, recommendations, streaks, reverse or mixed practice, Kanji/vocabulary progress, synchronizing unfinished rounds between devices, generic progress engines, background workers, WebSockets, analytics dashboards.

## Decisions

| Question                       | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Catalog sharing                | Move the M03.1 catalog, its helpers and the answer check unchanged into `packages/kana` (`@shiori/kana`), as planned in M03.1. Ids, pairings and readings did not change; their tests moved with them.                                                                                                                                                                                                                                                                                                                                    |
| Owner                          | New single-capability API module `modules/kana-progress`, table `kana_attempt`.                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Record identity                | Primary key `(user_id, round_id, question_index)`. The client creates a UUID per round; the question index is the position in the round. The same kana may appear many times in a round and across rounds.                                                                                                                                                                                                                                                                                                                                |
| When a question is final       | **Superseded by M03.3.1 and M03.4.1.** Originally: when the round moves past it (automatic advance, Next, Skip). Now a right answer or correction is final at submission, and a wrong answer awaiting correction is finalized as incorrect when **Start new round** replaces the round. See `docs/03-architecture.md`.                                                                                                                                                                                                                    |
| Stored fields                  | `kana_id`, `script` (derived on the server, CHECK-ed against the id prefix), `direction` (only `kana-to-romaji`), `outcome`, `corrected`, `hint_used`, server `created_at`. Catalog data (readings, forms) is not copied.                                                                                                                                                                                                                                                                                                                 |
| Submitted answer text          | Sent so the server can check it against the outcome with the canonical catalog, then discarded. Nothing reads it yet, so it is not stored.                                                                                                                                                                                                                                                                                                                                                                                                |
| Idempotency                    | `INSERT … ON CONFLICT DO NOTHING`, then compare the repeated occurrences with the stored rows in the same transaction. An identical retry counts as a duplicate (200); different data for a recorded occurrence returns 409 with the conflicting occurrences and records nothing from that batch.                                                                                                                                                                                                                                         |
| Batching                       | 1–100 attempts per request; the client sends each finished question at once and drains its queue in batches of up to 100.                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Ownership                      | Ownership always comes from the session. The request also carries the `userId` the client recorded the attempts for; a different session user gets 403. This stops a tab that still shows user A from writing A's attempts into user B's account after B signed in elsewhere in the same browser.                                                                                                                                                                                                                                         |
| Client queue                   | `localStorage['shiori:kana-attempts:<userId>']`, separate from the per-tab practice round in `sessionStorage`. An entry is removed only after a 200 (or a 409 that names it). Network and server failures retry with 2 s, 4 s, … 60 s delays, on **Try again now**/**Save now**, when the browser goes online and whenever a Kana page opens. A 400 moves the batch to `rejected`, kept on the device and reported (**superseded by M03.4.1**: only the entries the server names move, and refused results can be sent again or removed). |
| Sign-out and account switching | Pending entries stay under the original user's key, are never shown to or sent by another user, and are sent when that user signs in again on this browser.                                                                                                                                                                                                                                                                                                                                                                               |
| Statistics                     | `independentCorrect + assistedCorrect + incorrect + skipped = attempts`; `corrected` is reported separately. The tile bar shows `independentCorrect / attempts`; no mastery label.                                                                                                                                                                                                                                                                                                                                                        |
